## 1. Root

Libre Systems' DICOM UID root is **`1.3.6.1.4.1.67686`**.

It is built on IANA Private Enterprise Number **67686**, registered to Libre
Systems (contact Patrick Mulcahy, patrick@libresystems.org). Checked in
<https://www.iana.org/assignments/enterprise-numbers.txt> (issue #30).
`1.3.6.1.4.1` is the IANA "private enterprises" arc (iso.org.dod.internet.private.enterprise).

Every UID that Libre Systems software creates or uses to identify itself
must sit under this root and follow this registry. UIDs that belong to
others (DICOM's `1.2.840.10008`, a modality's UIDs, test data from other
projects) are never changed.

## 2. Approved layout (verbatim, 2026-11-17)

- `1.3.6.1.4.1.67686.1` = products: `.1.1` LibreDCM, `.1.2` Libre WT, `.1.3` LibreDVT, `.1.4` LibreKey
- `1.3.6.1.4.1.67686.1.1.1.<major>.<minor>` = LibreDCM Implementation Class UID; Implementation Version Name `LIBREDCM_<major>_<minor>` (e.g. `LIBREDCM_0_2`; max 16 chars, VR SH)
- `1.3.6.1.4.1.67686.2.<product>.<site>.<time>.<counter>` = UIDs generated by our products (manifests, rejection notes, coerced copies)
- `1.3.6.1.4.1.67686.9` = test data only, never in shipped product code paths

## 3. Rules for every UID (PS3.5 §9.1)

- Only the digits `0`–`9` and `.`; at most 64 characters.
- No empty component; no leading zero in a component of more than one digit
  (`0` alone is allowed).
- Checked in code by `dicomuid.Valid` (DCM-SRS-099).

## 4. Implementation Class UID and Version Name

Every product that speaks DICOM sends both values in each A-ASSOCIATE-RQ and
A-ASSOCIATE-AC (PS3.7 Annex D.3.3.2) and writes both in the File Meta of each
Part 10 file it writes: (0002,0012) Implementation Class UID and (0002,0013)
Implementation Version Name.

| Product | Implementation Class UID | Implementation Version Name |
|---|---|---|
| LibreDCM | `1.3.6.1.4.1.67686.1.1.1.<major>.<minor>` (approved) | `LIBREDCM_<major>_<minor>` (approved) |
| LibreDVT | `1.3.6.1.4.1.67686.1.3.1.<major>.<minor>` (*proposed*, same pattern) | `LIBREDVT_<major>_<minor>` |
| Libre WT | `1.3.6.1.4.1.67686.1.2.1.<major>.<minor>` (reserved; Libre WT does not speak DICOM) | `LIBREWT_<major>_<minor>` |
| LibreKey | `1.3.6.1.4.1.67686.1.4.1.<major>.<minor>` (reserved; LibreKey does not speak DICOM) | `LIBREKEY_<major>_<minor>` |

Rules:

1. `<major>` and `<minor>` come from the build version (the release tag
   without the leading `v`, e.g. `0.2.0-beta.1` gives `0.2`). The build
   version is the one source of truth: LibreDCM reads it from package
   `buildinfo`, set at build time with `-ldflags -X` (DCM-SRS-098).
2. A patch release keeps the UID of its minor version. A new minor or major
   version gets a new UID automatically.
3. A build without a release version (`dev`, `ci`, a local build) identifies
   as version `0.0` (`…1.1.1.0.0`, `LIBREDCM_0_0`). Version 0.0 is never
   released, so such a build can always be told apart from a release.
4. `<major>` and `<minor>` are each at most 999, so the Version Name always
   fits VR SH (16 characters: `LIBREDCM_999_999`). A version outside this
   range also identifies as 0.0.

## 5. UIDs generated by products

Layout: `1.3.6.1.4.1.67686.2.<product>.<site>.<time>.<counter>`. Code:
`platform/dicomuid.Generator` (DCM-SRS-099). No product uses it yet; it is
there for the IHE work (manifests, rejection notes, coerced copies).

| Component | Encoding |
|---|---|
| `<product>` | Product number from §2: 1 LibreDCM, 2 Libre WT, 3 LibreDVT, 4 LibreKey |
| `<site>` | A positive decimal integer. **Configured:** 1–999999, allocated per installation or node in the log in §8 and set in the product's configuration (the setting is defined when a product first uses the generator). **Default (not configured):** a random number from 1000000 to 2^40−1 (13 digits at most), drawn from the operating system's secure random source at first start and kept in the generator's state file. The two ranges never overlap, so a random site can never equal an allocated one |
| `<time>` | Microseconds since 1970-01-01T00:00:00Z (Unix time), decimal, no leading zeros (16 digits today, 17 digits from the year 2286) |
| `<counter>` | Decimal 0–999999: the number of UIDs already issued in the same microsecond. When it would pass 999999, `<time>` moves on by one microsecond |

Uniqueness and order:

- **Within one process:** each (time, counter) pair is issued once, under a
  lock, and pairs strictly increase, also when the system clock is set back
  (the generator keeps counting from the last pair).
- **Across restarts:** with a state file the generator records a time mark
  one second ahead of what it has issued (written atomically: temporary file,
  fsync, rename) and restarts after that mark, so a clock set back by any
  amount cannot repeat or reorder a UID. If the state file cannot be written
  the generator refuses to issue UIDs. A damaged state file stops the
  generator from starting. Without a state file a restart draws a new random
  site (or, for a configured site, relies on the clock).
- **Across nodes:** each node needs its own site. Configured sites are
  allocated once per node in §8. Two nodes with random sites collide only if
  they draw the same number (about 1 in 10^12) and issue in the same
  microsecond with the same counter.
- **Length:** at most 20 (`1.3.6.1.4.1.67686.2.`) + 1 + 1 + 13 + 1 + 17 + 1 +
  6 = 60 characters, within the 64 allowed. The generator checks every UID
  with `dicomuid.Valid` before returning it.

## 6. Test data (`1.3.6.1.4.1.67686.9`)

Only synthetic test data uses this arc. It is never used in shipped product
code paths: an architecture test fails if a non-test source file contains it
(DCM-SRS-100, `TestTestDataArcOnlyInTests`). Test-only fake packages
(`modules/*/internal/fake*`) may use it as long as only tests import them.

Sub-arcs (*proposed*, by product number):

| Arc | Use |
|---|---|
| `1.3.6.1.4.1.67686.9.1` | LibreDCM tests (`modules/dicom`) |
| `1.3.6.1.4.1.67686.9.2` | Libre WT tests and the fake LibreDCM (`modules/wt`) |
| `1.3.6.1.4.1.67686.9.3` | LibreDVT tests (reserved) |
| `1.3.6.1.4.1.67686.9.4` | LibreKey tests (reserved) |

Third-party test data (pydicom samples, gonetdicom fixtures under
`third_party/`) keeps its own UIDs.

## 7. Changing this registry

1. Arcs are permanent: never reuse or renumber an arc, even after a product
   is withdrawn. Mark it *retired* in §8 instead.
2. Only the owner allocates. An allocation is a document change under
   QMS-SOP-001: a pull request that adds a row to §8, linked to an issue.
3. Before allocating, check the new UIDs fit 64 characters for every value
   the components can take.
