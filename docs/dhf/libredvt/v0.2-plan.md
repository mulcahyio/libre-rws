## Decisions (Patrick Mulcahy, Telegram, 2026-11-19)

Patrick answered "Yes, start" to building v0.2 with the five open decisions
of this plan, all at the recommended default:

| ID | Decision |
|---|---|
| D1 | **Boundary:** association negotiation + TLS tests, and DICOMweb QIDO-RS / WADO-RS / STOW-RS. Storage Commitment, MPPS, MWL and emulators are deferred. |
| D2 | **DICOMweb auth:** localhost/no auth plus bearer-token plumbing with secret redaction. No OAuth server. |
| D3 | **TLS baseline:** TLS 1.2+, hostname verification, configurable CA, optional client certificate, no insecure bypass. |
| D4 | **Targets:** generic DICOM / DICOMweb systems from any vendor, plus a LibreDCM smoke plan (LibreDCM has no DICOMweb; its plan covers DIMSE + TLS). |
| D5 | No workflow protocol is required for the release gate. |

Why: LibreDVT will be used for Mulcahy.io client DICOM interoperability
audits and cybersecurity evidence (vault *Side Income Plan*). It stays a
validated QMS tool (QMS-SOP-011, high risk), not a medical device. The
production guard stays: store operations (C-STORE, STOW-RS) run only
against `lab`-class targets.

### Open decisions (safe defaults taken, to confirm)

Recorded in issue #34. Work continues on the default.

1. C-FIND against `production` targets stays allowed as in v0.1
   (DVT-SRS-028 unchanged). The new DICOMweb data steps (`qido`, `wado`,
   `stow`) run only against `lab` targets (DVT-SRS-134). **Default: yes.**
2. Bearer tokens over plain `http://` only to loopback hosts
   (DVT-SRS-112). **Default: yes.**
3. A TLS-version refusal check the image cannot perform (OpenSSL refuses
   to offer TLS 1.0/1.1) is an engine error, never a pass or a skip
   (DVT-SRS-105). **Default: yes.**

## Scope

1. **Association and transport security:** association negotiation
   assertions (presentation contexts, transfer syntaxes, rejection values,
   negotiated parameters, role selection), TLS client tests with certificate
   and host-name verification, mutual TLS, refusal checks (plaintext, old
   TLS, missing client certificate), TLS for the built-in Storage SCP.
2. **DICOMweb core:** QIDO-RS search, WADO-RS retrieve (instances and
   metadata), STOW-RS store, with strict HTTP status, content-type,
   multipart, metadata and pixel checks.
3. **Shared foundation:** protocol-specific targets with TLS and secret
   references, strict schema, protocol-neutral evidence model, redaction
   with scan-before-write, size limits, one request at a time.

## Explicit non-goals

- No reuse of LibreDCM's DICOM or networking libraries.
- No diagnostic viewer, PHI workflow, or deployment as part of the PACS.
- No broad DICOMweb conformance claim: the supported resources, media types
  and transfer syntaxes are stated in the user documentation.
- No emulators, Storage Commitment, MPPS or MWL (D1, D5).
- No OAuth, basic auth or certificate revocation checking (D2; known
  limitation recorded in `cybersecurity.md`).

## Architecture slices

1. Strict target and plan model with protocol-specific targets and shared
   TLS/secret configuration (`plan-schema.md`).
2. Worker commands for association inspection and TLS; Go orchestration and
   assertions.
3. Protocol-neutral result model with redacted evidence
   (`evidence-model.md`).
4. Test peers: Go TLS and DICOMweb test servers, DCMTK association peers,
   Go raw-socket PDU peer, certificate fixtures (synthetic CA, server,
   client, expired, wrong host).
5. UI/CLI target configuration and reports, v0.1 behaviour unchanged.
6. DHF updates: trace matrix, tool-validation record, manual verification,
   README, CHANGELOG.

## Verification and tool validation

- Positive controls: correct QIDO/WADO/STOW responses pass; wrong SOP UID,
  metadata, transfer syntax, multipart boundary, per-instance status, 202,
  206 and redirect fail.
- TLS controls: trusted certificate passes; expired, wrong-host,
  CN-only, unknown-CA, incomplete-chain, TLS 1.1-only and client-cert
  failures fail closed; refusal checks fail against servers that accept
  plaintext or TLS 1.1.
- Association controls: rejected or wrongly accepted context, other
  transfer syntax, other reject values, timeout, abort, close and garbage
  fail.
- Failure injection: missing worker, crash, hang, garbage JSON,
  schema-invalid JSON, malformed HTTP and truncated multipart give an
  engine/protocol error and a failed step.
- Secret check: every artefact grepped for the configured synthetic
  secrets; a secret injected into an error message fails the run.
- Mutation check: verdict flipped, host-name check off, unknown plan fields
  accepted, failed STOW instances ignored, zero-assertion step passed.
- Independent cross-check: Orthanc + DICOMweb plugin (digest-pinned, test
  container) for DICOMweb; DCMTK `+tls` for DIMSE/TLS. Peers never share
  the worker's libraries.
- The v0.1 positive controls and the LibreDCM plan run unchanged; DCMTK and
  LibreDVT both stay in release verification.
